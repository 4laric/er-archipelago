# SPEC: the publishing pipeline

**Status:** problem measured (§1-3), labelling shipped (§4.1, PR #468), channel design proposed
(§5, Alaric's beta/stable idea). Nothing in §4.2-4.5 or §5 is built. The decisions are in §6.

## 1. The thing that went wrong, in one paragraph

`wizard/wizard.html` is a static page that is deployed to <https://peliarch.ca/er/> by copying it,
on whatever schedule someone copies it. The apworld is published on a **git tag**, and a
player-facing bundle also goes to **Nexus**, on a third schedule. Nothing pins any of the three to
each other, so on 2026-08-08 all three were different builds of this project, and the newest of them
was the one strangers were being pointed at.

### 2.1 🛑 What Archipelago does with an option the installed apworld has never heard of

Measured, not assumed. AP 0.6.7, a yaml carrying two invented keys, generated against a world that
does not define them:

```
P1 Weights: t.yaml >> unknown-option probe
an_option_that_does_not_exist is not a valid option name for Elden Ring and is not present in triggers for player SkewTest.
keep_local_rune_cap_typo is not a valid option name for Elden Ring and is not present in triggers for player SkewTest.
...
Archipelago Version 0.6.7  -  Seed: 998
```

**Exit 0. The seed generated. The options were dropped.** Those two lines sit in the middle of ~50
`Could not load world` lines from unrelated worlds missing native deps, on a console nobody reads
when the thing worked.

So the failure mode of website-ahead-of-download is not an error, it is a **silent wrong answer**:
the player sets `keep_local`, the seed rolls, and their consumables go out to the multiworld anyway.
That is the exact class this repo spends most of its gates on, arriving through the one surface that
had no gate at all.

## 3. The three surfaces, and what actually pins each

| Surface | Fed by | Pinned by | Can go stale? |
|---|---|---|---|
| GitHub release | `package_release.ps1` off a tag | the tag | no — this one is correct |
| peliarch.ca `/er/` | a copy of `wizard/wizard.html` | **nothing** | yes, and it is the *ahead* one |
| peliarch.ca `POST /generate` | the apworld installed on the box | **nothing** | yes, and it can be *behind* the page it serves |
| Nexus | a manual upload | **nothing** | yes |

Two notes on the state of the docs:

* `release/DISTRIBUTION.md` says, under **What we do NOT do**: *"No mirrors. Not on Nexus, not in a
  Discord pin, not a re-upload 'for convenience'."* The repo nevertheless carries a maintained
  `release/NEXUS-DESCRIPTION.txt`, and Nexus is where the comment thread that prompted `keep_local`
  lives. **The policy and the practice disagree, and the practice is winning.** Whichever is right,
  they should not both be true in the repo.
* `RELEASE-CHECKLIST-v0.3.md` has no row for "deploy the wizard" and no row for "update Nexus".
  A checklist that does not mention a surface cannot keep it current.

## 4. Design

### 4.1 Make the pairing visible (SHIPPED WITH THIS DOCUMENT)

The page cannot know what the player installed, so it says what IT is:

* `wizard/options-metadata.json` gains **`apworld_version`**, taken from `contract.APWORLD_VERSION`
  at dump time. It sits beside the existing `source_sha256`, which is already a deterministic
  fingerprint of the whole option surface.
* The wizard header names it: *"These options are the ones in apworld v0.3.8 — if the version you
  installed is older, anything newer than it is ignored when the seed is generated, without an
  error."*
* Every emitted yaml carries it in **`description:`**, which is the only field that survives into
  anything anyone reads later — Archipelago echoes it in the generation log as
  `P1 Weights: <file> >> <description>` and stores it in the multidata:

```yaml
description: "generated by the ER options wizard 2026-08-08 for apworld v0.3.8, options 3279392e (preset: Defaults)"
```

A yaml comment would not do: comments do not reach the log, the multidata, or a bug report.

This does not PREVENT skew. It makes an existing skew answerable in one line by whoever is looking
at the seed, which is currently impossible.

### 4.2 Deploy the wizard from a tag, not from a merge

The site should serve the wizard **built at the newest release tag**, so the page and the download a
player is being pointed at are the same build by construction. Cutting a release becomes the thing
that moves the site. This is the change that removes the failure rather than labelling it.

Testers still need the current one, so: a second path (`/er/preview/`) served from `main`, with a
banner naming the commit and saying plainly that no released apworld has these options yet. Two
channels, both honest; today there is one channel that quietly claims to be the first while being
the second.

### 4.3 The host should say what it generated with

`POST /generate` on peliarch runs the box's own apworld. It should return, and the wizard should
display, the `APWORLD_VERSION` that actually rolled the seed — the same string the yaml asks for.
When they differ the wizard can say so, which is the one place in this whole pipeline where both
numbers are in the same process at the same time.

### 4.4 Give Nexus a defined role

Either it is a **link-only page** (matching `DISTRIBUTION.md` as written, and the courtesy the same
file extends to thefifthmatt), or it is a **real publish target** with a checklist row and the
version in the page title. Both are defensible; the status quo — an unversioned mirror the docs
deny — is the one that is not. Note `DISTRIBUTION.md`'s own argument against mirrors is *"a stale
mirror produces exactly the mismatched pair the design is trying to prevent"*, and a Nexus upload
sitting behind the tag is that, precisely.

### 4.5 Gates worth adding once §6 is decided

* **release job**: on a tag, build the wizard, publish it as a release asset, and (if 4.2 is taken)
  push it to the site — so "deploy" stops being a manual copy.
* **a drift check that is allowed to be red**: report, on every `main` build, how far the deployed
  option surface is behind. A window is *supposed* to be ahead of the tag; the number just has to be
  visible rather than discovered by a player in a comment thread.

## 5. Beta stream / stable release

Alaric's proposal, 2026-08-08, and it subsumes §4.2: instead of one channel that is sometimes ahead
of itself, run **two**, and say which is which.

### 5.1 🛑 The channel CANNOT live in the version number. Measured.

The obvious shape is `0.3.8-beta.1`. It does not work, and the reason is upstream's, not ours:

```
>>> Utils.tuplize_version('0.3.8')          Version(major=0, minor=3, build=8)
>>> Utils.tuplize_version('0.3.8-beta.1')   ValueError: invalid literal for int() with base 10: '8-beta'
>>> Utils.tuplize_version('0.4.0-rc1')      ValueError
```

`worlds/__init__.py:120` calls `tuplize_version(manifest["world_version"])` when it loads an apworld,
so a prerelease string in `archipelago.json` is not a cosmetic choice — it is a load-time crash.
This repo's own gate already says so (`test_gf_apworld_manifest.py`: `world_version` must match
`^\d+\.\d+\.\d+$`), and `contract.APWORLD_VERSION` is asserted equal to it, so the internal
number cannot carry a suffix either.

There is history here too: that same test's docstring records the client sitting at **`0.1.0-beta.4`
against apworld 0.2.0 for months**. A beta suffix has already cost this project a version drift once.

### 5.2 So the channel is a POINTER, not a suffix

Every published build keeps a strict `X.Y.Z` and a tag — which is what happens today. What changes is
that **the channel names a tag**, and promotion moves the pointer rather than rebuilding anything:

```
release/CHANNELS.tsv      channel   tag       promoted_on   note
                          beta      v0.3.9    2026-08-11    keep_local, the sent-out count
                          stable    v0.3.7    2026-08-02
```

| | beta | stable |
|---|---|---|
| GitHub release | yes, `prerelease: true` (a GitHub flag — costs the version string nothing) | yes |
| wizard | `/er/beta/`, bannered | `/er/` |
| Nexus | no | yes |
| cut when | whenever the window has something worth playing | when a beta has soaked |

Both channels serve a wizard **built at a tag**, so within a channel the page and the download are
the same build by construction. That is the actual fix from §4.2, and it survives either answer to
"how often do we cut".

### 5.3 What it costs, honestly

**Cutting becomes the common operation, not the rare one.** A tag is a lockstep bump across four
version sites in two repos (`contract.py`, `archipelago.json`, the client `Cargo.toml`, the generated
`contract_gen.rs`), so "cut a beta" is the same ceremony as "cut a release" is today. Betas would
have to get cheap or they will not get cut. That is the real work in this proposal and it is not in
the packaging, it is in the bump.

**It is also the fix for a defect we already have.** Right now every commit in an open window reports
the same `APWORLD_VERSION`, which is exactly the disease `0.2.0 names five contract shapes` was
filed under and exactly what stalled the dafranky67 diagnosis — a player says "I'm on the new
version" and is telling the truth about a build nobody can identify. Cutting a numbered beta per
playable state gives every build a name. CONTRIBUTING rule 15 (contract changes ⇒ version changes)
already points this way; a beta stream is that rule applied to the window instead of only to the
release.

### 5.4 Two things found while measuring this

* **The bare `eldenring.apworld` asset does not exist.** `DISTRIBUTION.md` promises two assets per
  tag — the player bundle and a bare apworld for hosts, with the reasoning that making a host pull
  "a 10 MB bundle with a game-mod DLL in it, to generate someone else's seed, is friction for
  nothing". Every release from v0.3.2 to v0.3.7 has exactly **one** asset, and it is **123.7 MB**.
  The scheme the doc argues for has never shipped, and the friction is twelve times what the
  argument assumed.
* **The audience is small** — 9 to 30 downloads per release. Worth knowing before building ceremony:
  the channel split should cost less than the confusion it removes.

## 6. The decision that is not mine

**How often does stable move?** The channel machinery in §5 is the same either way; what it cannot
decide is whether stable trails beta by days or by weeks, and that is a judgement about how much a
stranger on Nexus should be protected from a build that has only been played by one person.

The related one, if §5 is not taken: **does the single public wizard track the tag or `main`?**
Tracking the tag is the honest default (§4.2). The cost is that someone asking on Nexus for a feature
that is already merged gets told "next release" instead of "it's live" — a product call about how
this project feels to use, not a spec's to make.

Everything else in §4 works under any of these answers.
