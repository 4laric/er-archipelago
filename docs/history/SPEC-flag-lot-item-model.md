# SPEC: The flag→lots faithful model — N co-firing checks per shared flag

**Status:** DESIGN DRAFT v2 (Fable architecture pass, 2026-07-24; v1's one-check-per-flag premise
retracted — see §0.3) — for Opus/Alaric review.
**Branch context:** `feat/natural-progression-mode` @ f1d8c79. Client clone referenced: `fsac`.
**Doctrine (Alaric, verbatim intent):** *"We control the models here. We should be making models
that match the game data, not the other way around."* `ItemLotParam` hangs N lots on one
acquisition flag; the faithful projection is therefore **N checks on one flag** — each lot its
own location, its own shuffled item, its own suppression — all co-firing when the game sets the
flag. One-check-per-flag was never the game's rule, never AP's rule, and never the client's rule.
It was ours, and this spec retires it.

### 0.2 The capture is lossy and orphaned

`region_map.csv` (loaded at `gen_data.py:423`) has ONE row per flag, named after the lowest lot;
the scan that produced it is **not in the repo** (committed once at `affd4d0`, never regenerated;

### 0.3 The constraint that wasn't (v1 retraction)

v1 of this spec took "two live checks cannot share one flag" as a hard client constraint and
designed representative-selection + vanilla ride-alongs around it. **Verified false, in the
client source:**

- AP core tracks numeric location ids only; it has no concept of game flags and can enforce
  nothing about them.
- The client's poll table is **keyed by ap_id, not by flag**:
  `flagpoll.rs:16-21` — `location_flags: HashMap<i64, u32>` (AP location id → guarding flag),
  populated per location from slot_data at `core.rs:1078-1080`
  (`fp.location_flags.insert(loc, flag)`). Two ap_ids holding the same flag value are two
  distinct keys; nothing collides.
- The poll loop iterates **by location** with no per-flag dedupe: `core.rs:1786-1793` —
  `for (&loc, &flag) in &fp.location_flags { … if get_event_flag(flag) { to_check.push(loc) } }`.
  When a shared flag sets, EVERY location mapped to it is reported. N co-firing checks on one
  flag is behavior the shipped client already has.
- Adjacent machinery is flag-value-based and co-check-safe by construction: the new-save
  baseline (`core.rs:1652-1663`) and `set_known_collected_flags` (`core.rs:1099-1106`,
  `detour.rs:61`) key on flag values, applying uniformly to all of a flag's locations; sweeps
  (`core.rs:1801+`) fire member ap_ids off a flag exactly like co-checks would.

The ONLY enforcement of one-check-per-flag anywhere is **our own gen-side gate**:
`coverage.py:8` ("not aliased to another live location") enforced at `coverage.py:556-586`
(`by_flag` + the "aliased detect_flag" violation). A self-imposed rule — §4 relaxes it
precisely instead of deleting it.

## 1. The faithful capture: `flag_lots.tsv` (unchanged from v1)

A new **tracked, regen-reproducible** table, `greenfield/flag_lots.tsv`, one row per
(flag, table, lot, slot):

```
# AUTO-GENERATED by tools/datamine_flag_lots.py -- DO NOT EDIT. One row per ItemLotParam slot
# on a getItemFlagId. Sorted (flag, table, lot, slot). utf-8, \n, tab-separated.
flag	table	lot	slot	cat	raw_id	full_id	item_name	goods_type	evidence
510460	map	10460	1	1	2002901	…	Remembrance of the Impaler	3	emevd
510460	map	10461	1	1	2008021	…	Messmer's Kindling	1	emevd
```

- `flag` — `getItemFlagId` (and per-slot `getItemFlagId01..08` where set; `LOT_ITEMS` already
  reads all nine columns, `gen_data.py:452-456` — keep that fidelity).
- `table` — `map` | `enemy` (identity is load-bearing; same lot id can exist in both,
  `gen_data.py:3507-3526`).
- `cat`, `raw_id` — raw `lotItemCategory` / `lotItemId` (primary data).
- `full_id` — `raw | nibble` via the **derived** nibble map
  (`tools/gen_check_lots_table.py:131-184`; never re-declared).
- `item_name` — FMG name (convenience; identity joins on `full_id`).
- `goods_type` — `EquipParamGoods.goodsType` (key items are `goodsType==1`; gen_data already
  consumes this column, `gen_data.py:3892-3914`).
- `evidence` — does the game demonstrably AWARD this lot? `msb` (treasure reference, the
  `msb_flag_region.tsv` join), `emevd` (AwardItemLot site), `reward_family` (common.emevd
  $Event(1100)-class), or `none`. This drives the §2 minting gate: a lot in the params that
  nothing awards is real data but not a real pickup.

Matt-free: pure `ItemLotParam × EquipParamGoods × FMG × (MSB/EMEVD award-site)` join.
Deterministic sort + pinned encoding (the utf-8-sig lesson, `gen_data.py:417-422`).

**Emitter:** new `tools/datamine_flag_lots.py`, Windows-side (`build.ps1 -Greenfield`; artifacts
at `elden_ring_artifacts/vanilla_er/vanilla_er/`, `gen_data.py:17,444`). The in-repo,
re-runnable successor to the lost scan, for the item axis.

**Readers:** `gen_data.py` (replacing the artifact-only internals of `LOT_ITEMS` `:442-471` and
`_LOT_OF_FLAG` `:478-493`, keeping the artifact-side derivation as a regen drift cross-check

`tools/gen_check_lots_table.py`; the §8 tests. Net win: the faithful model becomes
sandbox-visible (today `LOT_ITEMS` is `{}` off-Windows and consumers silently degrade).

`region_map.csv` stays frozen, one row per flag — it is the location/region backbone and the
positional ap_id source (§2.2); `flag_lots.tsv` is the item backbone beside it.

## 2. The projection: each awarded lot is its OWN check

### 2.1 The rule

For every check flag (a flag surviving gen_data's row filters into `rows`), EVERY
`flag_lots.tsv` lot with `evidence != none` becomes a location:

- The **primary** co-check is the existing `region_map.csv` row — it keeps its ap_id, its
  region, its `flag_source`/`method`, and reverts to being named by its own lot (the lowest —
  which is what the scan named it after anyway, so raw CSV names are already correct:
  `510460 → "Remembrance of the Impaler"`, `400696 → "Ash of War: Flame Skewer"`,
  `520160 → "Redmane Knight Ogha"`, verified in the committed rows).
- Each sibling lot becomes a **secondary** co-check: same flag, same map/region/method/tags
  context as the primary (it is physically the same acquisition), its own `item_name` from its
  own lot, its own ap_id (§2.2), its own vanilla ware in the pool, its own suppression (§3).

Messmer's death is then TWO real checks — Remembrance AND Kindling — independently shuffled,
independently gateable, co-firing on flag 510460. No representative selection on the default
path; no ride-along demotion; **more checks, not fewer.**

Non-awarded lots (`evidence == none`) are NOT minted (a check whose vanilla pickup the game
never performs would inflate boss families like Gideon's 10060-10064 with content vanilla never
grants) — but they ARE ledgered (§2.4) so deliberate absence stays distinguishable from loss.
Note detection-wise they WOULD fire (detection is the flag); the gate is about item-model
honesty, and flipping a lot to `evidence != none` later is a one-line datamine improvement, not
a schema change.

### 2.2 ap_id minting without renumbering anything shipped

Positional ids cannot be used: `ap_id = BASE_AP + index into rows` (`gen_data.py:142,
2485-2486, 3792`), *"APPENDED, never inserted"* (`:2227`) — and even tail-appends are fragile
across regens when the appended SET grows (a new co-check discovered next month would shift
every co-check sorted after it).

So co-checks get an **allocation registry**: tracked `greenfield/co_check_ids.tsv`,
`(flag, table, lot) → ap_id`, **append-only**. gen_data reads it; any (flag, table, lot) that
qualifies (§2.1) but has no row gets the next free id, and the regen APPENDS the new rows —
the data-drift gate (`run_ci.ps1:224`) then forces the allocation to be committed, exactly like
every other generated artifact. Ids allocate from a reserved band, proposal
`COCHECK_BASE = 7900000` (current positional space tops out ≈ `7775300`; the band never
collides and is self-describing in logs). An id, once allocated, is never reused or re-derived
— delisting a co-check (evidence retracted, opt-out added) retires the id in place with a
ledger annotation.

Primary rows are untouched: every shipped ap_id keeps its meaning.

Gen-side consumers that inverse-map flag→ap_id must become co-check-aware; the audit found ONE:
`_flag2apid = {int(r["flag"]): BASE_AP + i …}` (`gen_data.py:3072`), feeding `REGION_BOSSES`
(`:3077`) and the sweep join (`:3100`). Rule: flag-keyed singular consumers bind to the
**primary** (boss entries, sweep triggers, `SHOP_ROW_FLAGS` joins); co-checks are additional
locations, never additional bosses/triggers. `MISSABLE_LOCATIONS` selection is flag-keyed
(`:3745-3753`) → extend to stamp every co-check of a selected flag (same physical acquisition ⇒
same missability). Location-keyed consumers (`LOCATION_ITEM`, `location_tags`, `checkItemFlags`)
need no rule — co-checks flow through them like any appended row.

### 2.3 slot_data / client

`locationFlags` simply gains the co-check entries (`ap_id → same flag`). No client change:
§0.3 shows the poll already fires all of them. Sweeps, baseline, collected-flags all key on
flag values and behave identically for every member.

### 2.4 Ledgers

- `NOT_RANDOMIZED` stays flag-keyed for whole-flag exclusions (`gen_data.py:2611-2626`).
- New `CO_CHECKS_NOT_MINTED = {(flag, table, lot): reason}` in generated data — `no_award_
  evidence` | `single_check_optout` | `retired` — the per-lot sibling of NOT_RANDOMIZED, same
  doctrine (`:2600-2609`: an unexplained absence must fail the regen, not ship quietly).

## 3. Suppression: each co-check blanks its OWN lot

Already 90% built. Our per-seed path (`gen_data.py:3541-3587` → `check_lots_data.py`
`CHECK_LOT_SLOTS_MAP/ENEMY` + `CHECK_LOT_ZERO_MAP/ENEMY`) is **lot-keyed and already blanks
every lot on a check flag** — under v1's one-check model that was the bug (it deleted the
sibling goods); under co-checks it is exactly correct: every lot's vanilla ware is blanked, and
every lot's ware re-enters the world as that co-check's pooled AP item. Nothing rides along
vanilla; nothing is deleted. The client side is confirmed per-lot
(`check_lots.rs:145-151, 208` — `blank_map: HashMap<u32 lot, Vec<u8> slots>`).

Changes needed:

1. **Scope the blank set to minted checks**: blank/zero the lots of primary + minted co-checks
   (+ opted-out flags' whole families, §6); a lot with `evidence == none` on an otherwise-live
   flag keeps its blank TODAY (it grants nothing anyway) — keep blanking it (harmless,
   belt-and-suspenders, zero diff).
2. **`check_lots_table.json` shape**: flag-keyed one-lot (`{"<flag>": {"lot": …, "slots": […]}}`,
   `tools/gen_check_lots_table.py:23-28`) becomes a **list per flag**:
   `{"<flag>": [{"lot": …, "slots": […]}, …]}` — the honest shape; the last-write-wins overwrite
   at `:258-262` dies. Coordinated change with `er-logic static_lots.rs` (foreign path) and
   `coverage._load_static_table` (`coverage.py:133-147`); version-gate the key
   (`"map_v2"`/`"enemy_v2"` beside legacy keys for one release, mirroring the
   `CHECK_LOT_SLOTS` legacy-key precedent in `features/check_lots.py:102-116`).
3. **Location→lot binding** for the gate and the tests: emit `LOCATION_LOT = {ap_id: (table,
   lot)}` into `check_lots_data.py` (primaries + co-checks). This is the join §4's invariant
   runs on.

`checkItemFlags` needs no structural change: each co-check contributes its own vanilla FullID
under its own flag via the existing merge (`features/check_item_flags.py:98-100`); the client
already suppresses-until-all-flags-collected per FullID (`:18-23`), and co-checks sharing a
flag collect together.

## 4. The coverage gate: relax no-alias into the co-check invariant

Replace the unconditional aliased-flag violation (`coverage.py:582-586`) with:

> **DETECTABLE (revised).** A detect flag shared by multiple live locations is legal **iff**
> the sharing set is a *declared co-check group*: (a) every member has a `LOCATION_LOT`
> binding; (b) the bound (table, lot) pairs are **pairwise distinct**; (c) every bound lot is a
> member of the flag's `flag_lots.tsv` family; (d) every bound lot is suppressed at that lot
> (its entry present in the static table's list for the flag AND emitted in
> `checkLotBlankMap/Enemy` — the existing `_classify_suppression` test, `coverage.py:526-533`,
> run per-member against ITS OWN lot, not against "any lot of the flag"); and (e) the group is
> complete: `{bound lots} == {family lots with evidence != none}` minus `CO_CHECKS_NOT_MINTED`
> entries. Any sharing that fails (a)-(e) is the SAME violation as today — genuine accidental
> aliasing (two unrelated locations landing on one flag) stays a hard failure with the same
> provenance text.

Two adjacent checks generalize mechanically:
- **AWARDED** (`coverage.py:590-625`): unchanged in spirit — the flag must have an awarding
  row; with (c)+(e) it sharpens to "this member's own lot awards".
- **SUPPRESSED**: per-member per-lot as (d); the `static_suppress` bit (`:442-443`) reads the
  list shape.

The gesture/event-award classes are untouched — gesture flags are asserted outside the lot
universe (`gen_data.py:2472-2478`; `coverage.py:169-174`) and can never be co-check groups.

## 5. Pool, counts, fill

- **Count-neutrality:** locations grow by exactly the minted co-checks, and — because the pool
  is built positionally from `LOCATION_ITEM` (each location contributes its own vanilla ware;
  unresolved → Rune filler, `gen_data.py:3791-3804` + core) — items grow by the same number.
  `items == locations` holds with no new accounting; the drift/count tests (§8) get updated
  pins, knowingly, with the diff as the review artifact (the anti-laundering rule at
  `gen_data.py:810-811`).
- **Fill:** co-checks are ordinary locations in the same region with identical access rules —
  "several locations become reachable/collected together" is AP fill's normal case (any region
  is that). No fill change. The one real consequence of co-firing is **you cannot obtain one
  without the other(s)**: both Messmer checks send on the kill. That is faithful (it is one
  physical acquisition) and logic-safe: reachability is per-location and identical across the
  group; sphere accounting treats them like two chests behind one door.
- **Classification symmetry:** missable/excluded/quarantine status must be uniform across a
  group (§2.2 MISSABLE rule; a gate check: no group may mix "excluded" and "live" members —
  add to §4(e)'s completeness test).
- **natural_progression:** gets what it wanted with no injection hacks — Messmer's Kindling and
  the Prayer Room Key become real pooled items as co-checks; `GATE_CLAUSES`
  (`natural_progression.py:137-143`) and the availability guards (`:198-215`) work unchanged.
  `GLOBAL_RECOVER[400032]` (Pureblood, `gen_data.py:1684-1691`) is orthogonal (a flag-level
  recovery, not a lot-split) and stays.

## 6. The exception path: single-check flags (representative selection survives here)

Co-check is the DEFAULT. A small opt-out table keeps judgment where judgment belongs:

```python
# flag -> the ONE lot that stays a check; every sibling lot is blanked and ledgered
# (CO_CHECKS_NOT_MINTED: single_check_optout). For families where a second check is
# wrong: junk/duplicate sibling goods, flags set for non-pickup reasons, or a
# deliberate pool-shape call. Each entry cites why. Ships SMALL.
SINGLE_CHECK_FLAGS = { ... }
```

Under opt-out: one check, named by the chosen lot (this is v1's representative selection,
demoted to the exception path — the deterministic priority rule from v1 [key-item goodsType==1
> Great Rune > Remembrance > category-important > non-repeatable > tier > lowest lot] survives
as the *suggested default* the gen report prints beside each opt-out, so an entry that just
re-picks the derived answer is flagged as dead weight); every sibling lot blanked (today's
behavior, deliberately chosen instead of accidentally inherited).

**510440 (Thorns + Scadutree Fragment):** the candidate case. Co-check default would mint BOTH
— Thorns stays pooled (the Shadow Keep / Rauh nat-prog gate key, `natural_progression.py:
126-130`) AND the 46th Fragment enters the pool. That actually dissolves v1's ambiguity —
recommend **no opt-out**; both checks. The opt-out table likely ships empty or near-empty,
which is the correct smell.

## 9. Risks / open questions

1. **Static-table shape change is a client-contract change** (`static_lots.rs` + coverage
   loader). Version-gated dual-key for one release; the foreign (Bedrock) path meanwhile keeps
   legacy behavior — no worse than today.
2. **Evidence quality** decides the minted population. `msb_flag_region.tsv` + EMEVD award
   sites cover the confirmed families; lots with `evidence == none` (NG+/multiplayer variants,
   Gideon-family extras) stay unminted + ledgered until proven. Under-minting is safe
   (status quo per lot); over-minting inflates the pool with never-granted goods — the gate
   errs under.
3. **Pool/balance shift:** up to ~1079 map + 93 enemy new checks IF all had evidence — realistic
   first regen will mint far fewer; the regen report must print the minted count and the
   evidence histogram before anyone commits it.
4. **Co-fire UX:** two "sent" toasts per shared-flag pickup. Cosmetic; the notif ticker already
   batches sweeps, same mechanism applies.
5. **`_flag2apid`-shaped assumptions** outside gen_data (any script inverse-mapping flag→ap_id):
   audit found only `gen_data.py:3072`; the §8.2 test catches regressions structurally
   (a co-check group member appearing as a boss/sweep trigger fails uniqueness).
6. **510440**: recommend co-check (both Thorns and Fragment pooled) — needs Alaric's ack since
   it adds a 46th Fragment to the pool with count-gate implications (deferred K-fragment gate,
   `natural_progression.py:56`).
7. **Does anything rely on one-check-per-flag?** The gate itself (relaxed here, §4);
   `key_resolver` (foreign slot keys, `core.rs:669`) never sees greenfield co-checks; nothing
   else found. The in-game ledger claim "the Remembrance rides along … the accepted tradeoff"
   (`gen_data.py:656-658`) is superseded — the Remembrance comes back as a check.
